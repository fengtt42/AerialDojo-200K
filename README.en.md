# AerialDojo Dataset Structure

[中文](README.md) | English

This README describes the complete local dataset layout: environments, navigation tasks,
planned trajectories, and recorded observations. See
[AerialDojo/README.en.md](AerialDojo/README.en.md) for code usage.

**The current GitHub release contains code, Chinese/English READMEs, and dataset directory
markers.** Environments, tasks, trajectories, and images will be published separately on
Hugging Face; download links will be added here. Cloning the GitHub repository does not
download the data. Once available, place the data directories at the repository root,
keeping the relative paths below. Recording and online evaluation require the relevant
environment and task data first.

## 1. Directory layout

```text
AerialDojo/
├── README.md / README.en.md     # Chinese and English dataset documentation
├── AerialENVS/                  # Packaged UE / ProjectAirSim environments
│   ├── IID_ENVS/
│   └── OOD_ENVS/
├── SemanticOGS/                 # Text-goal navigation tasks
├── ImageOGS/                    # Image-goal tasks and reference images
├── TrajectoryDATA/              # One planned trajectory per task
├── VideoRECORD/                 # Recorded RGB, depth, poses, and actions
├── BENCHMARK/                   # Currently reserved
└── AerialDojo/                  # Code project with its own usage README
```

| Directory | Contents | Intended use |
| --- | --- | --- |
| `AerialENVS` | Packaged UE environments with ProjectAirSim | Run scenes on a Linux GPU server |
| `SemanticOGS` | Start poses, goals, descriptions, landmarks, and task attributes | Text-goal navigation and task analysis |
| `ImageOGS` | Corresponding image-goal tasks and target reference images | Image-goal navigation |
| `TrajectoryDATA` | Planned pose and action sequences | Route analysis, playback, and recording |
| `VideoRECORD` | Observations and metadata generated by the recorder | Training, visualization, and post-processing |

SemanticOGS and ImageOGS provide two goal representations for the same navigation tasks;
do not add their counts when reporting the number of distinct tasks. TrajectoryDATA does
not contain RGB-D observations along the route. VideoRECORD is generated on demand, so
an existing directory does not imply that recording is complete. Reading dataset files
offline does not require UE.

## 2. Environment names and splits

Environment names follow `<category>_<family>_<scene index>`, for example `N_Island_0`.

| Prefix | Category | Examples |
| --- | --- | --- |
| `N` | Natural | `N_Island_0`, `N_Coast_0` |
| `U` | Urban | `U_Mall_0`, `U_Factory_0` |
| `I` | Infrastructure | `I_Bridge_0`, `I_RailCorridor_0` |
| `D` | Disaster | `D_Earthquake_0`, `D_Flood_0` |

The current release assigns `_0` environments to IID and `_1` environments to OOD:

| Task split | Environment directory | Meaning |
| --- | --- | --- |
| `IID_TRAINS` | `AerialENVS/IID_ENVS` | Training tasks in IID environments |
| `IID_TESTS` | `AerialENVS/IID_ENVS` | Test tasks in IID environments |
| `OOD_TRAINS` | `AerialENVS/OOD_ENVS` | Provided training/adaptation tasks in OOD environments |
| `OOD_TESTS` | `AerialENVS/OOD_ENVS` | Test tasks in OOD environments |

Train and test tasks for a map use the same UE scene. Splits are defined over directed
task point pairs; target actors, semantic categories, and landmarks are not necessarily
disjoint. Experiments that adapt on OOD_TRAINS should be distinguished from experiments
that evaluate generalization without such adaptation.

Environment launchers are located at
`AerialENVS/<IID_ENVS or OOD_ENVS>/<map>/<map>.sh`.

## 3. Task categories and partitions

SemanticOGS, ImageOGS, and TrajectoryDATA share this partition structure:

```text
<split>/<task category>/<map>_<B|S|L>_<Train|Test>/
```

| Task category directory | Suffix | JSON `task` value | Completed-length range in the current generator |
| --- | --- | --- | --- |
| `1_BaseTasks` | `B` | `base_task` | `[5, 30)` meters |
| `2_StandardTasks` | `S` | `standard_task` | `[30, 60)` meters |
| `3_LongHorizonTasks` | `L` | `long_task` | `>= 60` meters; the upper bound can be configured per map |

Completed length is the translational path length plus the residual distance from the
last pose to the goal. Published tasks are already filtered, categorized, and split;
use their existing directories and fields without reclassifying them.

## 4. One-to-one episode correspondence

**Every partition has its own episode numbering, from `0` to `N-1`. Within that same
partition, SemanticOGS tasks, ImageOGS tasks, and TrajectoryDATA files correspond
one-to-one by `episode_id`.**

For the partition `IID_TRAINS/1_BaseTasks/N_Island_0_B_Train`:

```text
SemanticOGS/IID_TRAINS/1_BaseTasks/N_Island_0_B_Train/Task.json
ImageOGS/IID_TRAINS/1_BaseTasks/N_Island_0_B_Train/Task.json
TrajectoryDATA/IID_TRAINS/1_BaseTasks/N_Island_0_B_Train/
├── 0.json
├── 1.json
├── 2.json
└── ...
```

| Record in SemanticOGS/Task.json | Record in ImageOGS/Task.json | File in TrajectoryDATA |
| --- | --- | --- |
| `episode_id = "0"` | `episode_id = "0"` | `0.json` |
| `episode_id = "1"` | `episode_id = "1"` | `1.json` |
| `episode_id = "2"` | `episode_id = "2"` | `2.json` |
| `episode_id = "n"` | `episode_id = "n"` | `n.json` |

A complete partition with N semantic tasks therefore has N image tasks and N trajectory
files. Both Task.json files contain arrays. Select the record by episode_id and use that
ID as the trajectory filename.

Distinguish these identifiers:

- **episode_id is local to a partition.** Numbering restarts for each map, task category,
  and Train/Test split. Their `0.json` files represent different tasks. A global task key
  must include the full partition path and episode_id.
- **The trajectory's internal task_id is the planner's identifier.** It may differ from
  episode_id and is not the published trajectory filename.
- **Reference image names are not episode IDs.** Resolve the ImageOGS record's `image`
  field. Multiple tasks may reference the same target image.
- **Actor names are not task IDs.** The same actor may participate in multiple tasks or
  anchors, so actor names alone cannot uniquely identify an episode.

For example, episode 7 in `N_Island_0_B_Train` corresponds only to episode 7 in that exact
partition across the three data directories. It has no numbering-based relationship to
episode 7 in `N_Island_0_B_Test` or `N_Island_0_S_Train`.

## 5. SemanticOGS task fields

Each partition's Task.json is a JSON array, with one navigation task per element.

| Field | Meaning |
| --- | --- |
| `episode_id` | Partition-local task ID, stored as a string |
| `map_name` | Environment name |
| `coordinate_system` | ProjectAirSim NED in the published data |
| `start_true_name` / `goal_true_name` | Human-readable start/goal object names |
| `start_object_name` / `goal_object_name` | UE actor names |
| `start_pose.start_position` | Start xyz, in meters |
| `start_pose.start_quaternion_xyzw` | Start quaternion in xyzw order |
| `goal_pose.goal_position` | Goal anchor xyz, in meters |
| `category` | Goal semantic category |
| `Landmark` | Text describing the associated landmark |
| `Direction` | Direction description |
| `description` | Textual description of the target object |
| `task` | base_task, standard_task, or long_task |
| `used-in-train` | 1 for training, 0 for testing |
| `info.geodesic_distance` | Planned translational path length, in meters |
| `info.euclidean_distance` | Straight-line start-to-goal distance, in meters |
| `info.complexity` | Completed length divided by straight-line distance |

Complexity includes the final residual distance and can therefore differ slightly from
geodesic_distance / euclidean_distance. Filtering thresholds may vary by map; do not
reinterpret all published tasks using one fixed threshold.

## 6. ImageOGS goals

ImageOGS shares the task split, episode_id, start pose, and goal with SemanticOGS.
It supplies a reference image through `image` and omits the semantic task's `description`
and `Direction` fields.

Resolve `image` relative to **the directory containing its Task.json**, typically
`Images/<filename>.png`. Copy the referenced Images files together with image-goal tasks.
These images describe the target; they are not observations captured along the route.

## 7. TrajectoryDATA fields

Each `<episode_id>.json` contains one JSON object.

| Field | Meaning |
| --- | --- |
| `schema_version` | Trajectory format version, such as hybrid_astar_trajectory_v6 |
| `map_name` | Environment name |
| `task_id` | Original planning task ID |
| `status` | Planning status |
| `start` | Start actor, position, and orientation |
| `goal` | Goal actor, position, radius, and boundary definition |
| `trajectory` | Ordered pose/action sequence |
| `trajectory[].position_ned_m` | Pose position in NED meters |
| `trajectory[].quaternion_xyzw` | Orientation in xyzw order |
| `trajectory[].action` | Action used to reach this pose |

The first item has action `start`. Each later action describes the transition from the
previous pose to that item. The final item need not contain `stop`. The goal is usually
a region, so the last pose need not exactly equal the goal anchor.

Published tasks and trajectories use **NED positions in meters and [x, y, z, w]
quaternions**. Positive NED z points down, and z is not height above ground. Replaying
published data does not require another UE-to-NED conversion.

## 8. VideoRECORD observations

Recording retains the split and task category directories, but omits the trailing
`_Train` / `_Test` from the map partition folder:

```text
VideoRECORD/IID_TRAINS/1_BaseTasks/N_Island_0_B/
├── 0/                           # Original episode_id="0"
│   ├── step_*_camera_*.png       # Front, left, right, down RGB
│   ├── depth/*.npy              # Corresponding depth frames
│   ├── trajectory_*_collected.jsonl
│   └── .recording_complete.json
└── collected_episodes.json      # Partition recording index
```

The default image size is 640×640. RGB is stored as PNG; DepthPerspective is stored as
float32 NPY in meters. Metadata preserves the original episode_id, planner task_id,
task source, and per-frame poses/actions.

`VideoRECORD/collected_episodes.jsonl` combines recording metadata. Use the unique
`recording_id` across partitions, not episode_id alone. A recorded frame's action is
the **next action after that observation**, and the final frame has action stop. This
shifts the action association by one item relative to the original trajectory sequence.

The recorder produces individual frames, not MP4 files. Image references may contain
absolute paths from the recording machine; update those paths when moving recordings.

## 9. Current audit and known limitations

A read-only audit of the complete local dataset before publication on 2026-09-28
covered 252 partitions across 42 maps, containing
102,866 navigation tasks and their trajectories. Episode associations, shared task
fields, and trajectory start/goal bindings passed. All 9,504 referenced goal image
files passed readability checks and have dimensions of 640×640. This audit did not
revalidate planning results, check collisions, or launch UE.

- **One environment package is missing:** `AerialENVS/OOD_ENVS/U_Community_1` does
  not exist. Its 394 tasks and trajectories are provided, but the environment package
  must be added before running or recording them. Launchers, referenced main binaries,
  and pak files exist for the other 41 maps.
- **Twelve long-horizon partitions are empty:** the partitions below have empty
  Task.json arrays and corresponding empty trajectory directories. This is not a
  task-to-trajectory mismatch. Skip empty partitions in batch loading and statistics,
  and avoid division by zero.
- **VideoRECORD has no recorded episodes yet:** only placeholder directories exist.
  Follow the code README to capture RGB-D observations along the routes.
- **Online evaluation requires input preparation:** online YAML files still reference
  unavailable `example/...` files, and the online start-quaternion field and trajectory
  format differ from the published format. See
  [section 4 of the code README](AerialDojo/README.en.md#4-online-policy-evaluation)
  for conversion requirements. The recorder directly supports the published format.

| Empty long-horizon partitions | Maps |
| --- | --- |
| Both Train and Test | D_Earthquake_0, D_Explosion_0, D_Flood_0, N_Forest_0, U_ParkingLot_1 |
| Train only | N_Mountain_1 |
| Test only | N_Snowfield_0 |
